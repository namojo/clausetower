# ClauseTower 구성 검토와 검증

해커톤에서 문제가 되는 것은 "코드가 아름다운가"가 아니라 **심사위원이 받아서 돌렸을 때 되는가, 데모가 끝까지 도는가, 문서의 숫자가 맞는가, 위험한 노출이 없는가**다. 지적과 심각도는 모두 이 기준으로 잰다.

## 검토 절차

1. 게이트 결과 JSON(`_workspace/01_qa_gates.json`)의 `summary`, `env`, 실패 게이트를 먼저 읽는다. 측정으로 이미 드러난 문제부터 원인을 잡는다.
2. `references/dimensions.md`에서 맡은 관점의 점검 목록을 연다. 항목마다 확인하고 `checked`에 "항목: 결과 한 줄"로 남긴다. 문제없는 항목도 남겨야 검토 범위가 보인다.
3. 문제를 찾으면 재현한다. 명령으로 재현할 수 있으면 명령과 출력 일부를, 코드로만 확인되면 `파일:줄`과 인용을 근거로 붙인다.
4. 반대 증거를 찾는다. 이미 다른 코드·시험·문서가 막고 있는지 확인하고, 막고 있으면 보고하지 않는다.
5. 심각도와 수정 담당을 정하고 최소 수정안을 쓴다.

## 심각도

| 등급 | 기준 | 예 |
| --- | --- | --- |
| `blocker` | 데모·심사 절차가 실제로 깨진다 | 웹 엔진과 파이썬 숫자 불일치, 배포 워크플로 실패, README 빠른 시작 명령이 그대로는 안 돈다 |
| `high` | 심사위원 PC에서 재현이 실패하거나, 보안·개인정보 노출이 실제로 열린다 | 로컬 도우미가 임의 웹사이트의 요청을 받아 사용자 구독으로 LLM을 호출, 사내망에서 시험 다수 실패 |
| `medium` | 심사에서 지적받을 만한 견고성·일관성 문제 | 비편집 설치에서 경로가 깨짐, 문서 간 숫자 불일치, 지표 정의가 다른 숫자를 같은 이름으로 씀 |
| `low` | 다듬기 | 도움말 문구 누락, 용어 표기 흔들림 |

심각도는 "실제로 일어나는가 × 해커톤에서 누가 보게 되는가"로 정한다. 이론상 위험이지만 데모 경로에서 닿지 않으면 한 단계 낮춘다.

## 지적 형식

| 필드 | 내용 |
| --- | --- |
| `title` | 한 문장. 무엇이 어떤 조건에서 잘못되는지 |
| `severity` | 위 표 |
| `kind` | `defect`(코드 결함), `env`(환경 요인이지만 대응 필요), `risk`(확인 못 한 잠재 위험), `doc-error`(문서가 사실과 다름), `doc-gap`(해커톤에 필요한 문서·절이 없음) |
| `files` | 관련 파일 경로 |
| `evidence` | 재현 명령과 출력 일부, 또는 `파일:줄` 인용 |
| `repro` | 확인 명령 한 줄(있을 때). 검증자와 QA가 그대로 실행한다 |
| `impact` | 해커톤 영향: 누가 언제 무엇을 겪는가 |
| `fix` | 최소 수정안. 수정 위치와 방법 |
| `fix_owner` | `code`(ct-fixer), `docs`(ct-doc-writer), `user`(사용자 결정·외부 조치. 예: 저장소 설정, 키 회전) |
| `effort` | `S`(1시간 이내), `M`(반나절), `L`(그 이상) |

## 지키는 것

- **설계 원칙을 바꾸는 제안을 하지 않는다.** 돈 계산은 결정적 코드가 한다, 면책 적용은 `has_clause ∧ event_covered ∧ notice_ok ∧ 조건 충족`으로 기계적으로 결합한다, 웹 엔진은 파이썬과 같은 숫자를 낸다, LLM 실패는 정답지로 대체하고 횟수를 남긴다. 이 원칙과 충돌하는 문제를 찾으면 원칙을 지키는 수정안을 낸다.
- **재작성을 제안하지 않는다.** 해커톤 직전의 큰 변경은 데모 위험을 키운다. 수정 범위가 `L`이면 대안(문서로 한계 명시, 설정으로 끄기)을 함께 적는다.
- **가상 데이터 전제를 존중한다.** 고객·계약·사건은 가상이고 정답지는 팀이 썼다. 이것 자체는 지적하지 않되, 문서가 이 한계를 숨기면 `doc-error`다.
- **추적 파일을 바꾸지 않고, 과금 명령을 실행하지 않는다.**

## 검증 절차(ct-verifier)

검증자는 지적을 반박하는 입장에서 시작한다.

1. `repro`가 있으면 그대로 실행한다. 환경 보정 없이 한 번, 필요하면 게이트 스크립트와 같은 보정을 적용해 한 번 더 실행하고 두 결과를 함께 적는다.
2. `evidence`의 `파일:줄`을 직접 열어 인용이 실제로 있는지, 문맥상 지적이 맞는지 확인한다.
3. 반대 증거를 찾는다: 이 문제를 막는 다른 코드, 이미 있는 시험, 문서에 적힌 한계.
4. 해커톤 영향으로 심각도를 다시 잰다.
5. 판정한다.

| 판정 | 조건 |
| --- | --- |
| `confirmed` | 직접 재현했거나 코드·출력으로 확인했다. 반대 증거가 없다 |
| `refuted` | 재현되지 않거나, 이미 다른 곳에서 막혀 있거나, 지적의 사실 관계가 틀렸다 |
| `uncertain` | 재현 환경이 없거나 판단이 갈린다. 무엇이 있으면 판정할 수 있는지 적는다 |

여러 관점으로 검증할 때(철저 모드)는 프롬프트가 지정한 렌즈 하나에 집중한다.

| 렌즈 | 묻는 것 |
| --- | --- |
| `reproduce` | 지금 이 저장소에서 실제로 일어나는가 |
| `counter-evidence` | 이미 막혀 있거나 지적의 사실 관계가 틀리지 않았는가 |
| `impact` | 해커톤에서 누가 겪는가, 심각도가 과장되지 않았는가, 수정안이 원칙을 깨지 않는가 |
