# ClauseTower 평가 방법

기술 심사위원이 숫자가 어떻게 만들어졌고 어디까지 믿을 수 있는지 판단할 때 읽는 문서다. 숫자는 2026-11-02에 다시 잰 게이트 결과(`_workspace/04_qa_gates_r2.json`의 `facts`)와 추적 중인 측정 파일(`eval/results/`)에서 가져왔다. 실제 모델의 호출·비용·시간은 `eval/results/real*/run.log`에서 가져왔다. 숫자의 기준 문서는 [README 6절](../README.md#6-측정-결과)이다. `_workspace/`는 팀 PC의 게이트 출력이라 저장소에 없다. `facts.*`는 그 파일의 키이며, 같은 숫자는 [README 8절](../README.md) 검증 절차의 명령이나 추적 파일(`eval/results/robustness.md`, `eval/results/extraction_*.json`, `eval/results/real*/run.log`)로 다시 확인할 수 있다.

함께 보는 문서: [README](../README.md), [설치·실행 가이드](setup-guide.md)(설치와 환경), [아키텍처](architecture.md)(계산 규칙), [심사 예상 질문](judge-qa.md), [실제 모델 결과 폴더 설명](../eval/results/real/README.md).

## 1. 평가 질문

평가는 세 가지 질문에 답하려고 설계했다.

| 질문 | 무엇으로 답하나 | 결과 위치 |
| --- | --- | --- |
| Q1. LLM이 계약서를 읽어 만든 조건과 면책 판단이 배상금 계산에 쓸 만큼 정확한가 | 실제 모델 보고서를 정답지와 항목별로 대조 | 4절 |
| Q2. 배상 노출 순이 마감 임박 순(기존)보다 배상금을 줄이는가. 한 번의 우연이 아닌가 | 같은 시뮬레이터에서 정책 비교. 화물 배치를 시드 30개로 바꿔 반복 | 5절 |
| Q3. 웹 데모가 보여 주는 숫자가 파이썬 구현과 같은가 | JS 엔진과 파이썬 보고서 대조 | 6절 |

Q1과 Q2는 서로 독립이다. 정책 비교(Q2)의 숫자는 계약 조건에 정답지를 쓴 mock 모드 값이라, 모델 정확도(Q1)와 따로 선다. 실제 모델이 읽은 조건으로 정책 비교를 다시 돌린 결과는 4-3절에 있다.

## 2. 정답지 구성

계약서 8부(`contracts/*.md`)는 가상 데이터다. 정답지(`contracts/golden/*.yaml`)는 계약서와 같은 팀이 썼다. 고객마다 계약 조건(`terms`) 하나와 시나리오 3종별 면책 판단(`judgments`)이 들어 있다.

### 2-1. 계약 조건 106항목을 세는 방법

`eval/run_eval.py`의 `extraction`은 고객마다 아래 항목을 정답지와 비교한다.

| 묶음 | 항목 | 고객당 개수 |
| --- | --- | ---: |
| 금액 항목(`TERM_FIELDS`) | `basis`, `rate_pct`, `grace_hours`, `cap_pct`, `cap_amount_krw`, `cap_scope`, `base`, `base_amount_krw`, `flat_amount_krw` | 9 |
| 불가항력 항목 | `fm_present`(조항 유무), `fm_notice_hours`(통지 시한), `fm_conditions`(정성 조건 **개수**), `fm_events`(열거 사유 **개수**) | 4 |
| 계약에 따라 추가 | `tiers`(누진 구간, 미래식품), `flat_escalation`(가중 정액, 가온헬스케어) | 0~1 |

13항목 × 8곳 = 104항목에 미래식품과 가온헬스케어의 추가 항목 1개씩을 더해 106항목이다. 채점 파일의 고객별 `fields`가 A·B·C·F·G·H 13, D·E 14다(`eval/results/extraction_typhoon.json`).

불가항력의 정성 조건과 열거 사유는 **개수만** 비교한다. 내용이 같은지는 보지 않는다(8절).

### 2-2. 면책 판단 32필드를 세는 방법

고객 8곳 × 4필드다. 필드는 `has_clause`(조항 있음), `event_covered`(사유 해당), `notice_ok`(통지 충족), `applies`(최종 적용)다. 정성 조건별 충족 여부(`conditions_met`)는 채점하지 않는다. `applies`는 모델 값이 아니라 코드가 `has_clause ∧ event_covered ∧ notice_ok ∧ 조건 충족`으로 다시 만든 값이다(`src/clausetower/extract.py`).

정답지에는 시나리오 3종의 판단이 있지만, 실제 모델은 태풍 상륙과 항만 적체 2종만 돌렸다. 자사 WMS 장애는 실제 모델로 재지 않았다.

## 3. 지표 정의

정의는 `eval/run_eval.py`의 `extraction()`에 있다. 문서마다 아래 이름을 쓴다.

| 지표(코드 키) | 문서 이름 | 분모 | 정의 |
| --- | --- | --- | --- |
| `term_field_accuracy` | 계약 조건 추출 정확도 | 106항목 | 2-1절 항목 중 정답지와 같은 비율 |
| `judgment_accuracy` | 면책 판단 필드 정확도 | 32필드 | 2-2절 4필드를 고객마다 따로 센 정답 비율 |
| `applies_accuracy` | 최종 적용 여부 정확도 | 고객 8곳 | 고객별 `applies`(면책 결론)가 정답지와 같은 비율 |
| `citations_verbatim_rate` | 인용 원문 일치율 | 고객 8곳 | 고객의 모든 인용에서 첫 조각(`…` 앞)의 앞 20자가 계약서에 있는 고객 비율 |
| `citations_strict_rate` | 엄격 인용 일치율 | 고객 8곳 | 인용을 `…`와 ` / `로 나눈 조각 하나하나가 통째로 계약서에 있는 고객 비율. 공백·줄바꿈 차이만 무시 |
| `llm_fallbacks` | mock 대체 횟수 | – | LLM 호출 실패로 정답지·자리표시자로 대체한 횟수. 0이 아니면 정확도가 실제보다 높게 나온다 |

**판단 필드 정확도와 최종 적용 여부 정확도는 다른 지표다.** 판단 필드 정확도는 필드 단위라서 최종 적용 여부 정확도보다 높게 나온다. 예를 들어 항만 적체 2회차에서는 세움건설과 누리에너지의 `applies` 2필드만 틀렸다. 그래서 판단 필드 정확도는 93.8%(30/32)이고, 최종 적용 여부 정확도는 75%(6/8)다. 고객 단위로는 8곳 중 2곳의 면책 결론이 정답지와 갈렸다.

**인용 일치율은 두 개다.** 문서에서 "인용 원문 일치율 100%"라고 쓰는 숫자는 기존 정의(`citations_verbatim_rate`, 앞 20자)다. 앞부분만 맞추고 뒤를 꾸민 인용을 걸러 내려고 엄격 지표(`citations_strict_rate`)를 따로 추가했다. 기존 정의를 바꾸지 않은 이유는 정답지 인용이 조항 문구를 줄여 적었기 때문이다. mock 보고서를 엄격 기준으로 채점하면 0.75(8곳 중 6곳)가 나온다(`python eval/run_eval.py extraction out/demo/report_typhoon.json`, 2026-11-02 실행). 실제 모델 보고서 4개(1·2회차 × 시나리오 2종)는 두 기준 모두 100%다. 인용 검사 대상은 계약 조건 추출의 인용(`citations`와 불가항력 조항 인용)이다. 면책 판단의 인용은 채점하지 않는다.

**mock 모드의 정확도 100%는 의미가 없다.** mock은 정답지를 그대로 쓰므로 계약 조건·판단 정확도가 당연히 100%다. 실제 모델 정확도는 저장된 실제 보고서로만 말한다.

### 4-3. 틀린 항목의 성격

**계약 조건(2회차 5항목).** 과금 방식·요율·유예·상한 같은 금액 항목은 두 회차 모두 전부 맞았다. 틀린 항목은 모두 불가항력의 개수 항목이다.

| 고객 | 항목 | 모델 | 정답지 | 무엇이 달랐나 | 회차 |
| --- | --- | ---: | ---: | --- | --- |
| 세움건설 | `fm_conditions` | 3 | 0 | 12h 서면 통지 등을 정성 조건으로도 적음 | 1·2 |
| 바로유통 | `fm_conditions` | 1 | 0 | 통지 요건을 정성 조건으로도 적음 | 1·2 |
| 누리에너지 | `fm_conditions` | 2 | 0 | 포괄 사유("합리적으로 통제할 수 없는 사유")와 통지를 조건 쪽에 적음 | 1·2 |
| 누리에너지 | `fm_events` | 4 | 5 | 위 포괄 사유를 열거 사유에서 뺌 | 1·2 |
| 한빛전자 | `fm_events` | 7 | 8 | "폭설 등 천재지변"을 한 사유로 묶음 | 2만 |

**면책 판단(항만 적체).** 1회차는 누리에너지 1건, 2회차는 누리에너지와 세움건설 2건이 갈렸다. 모두 `applies`만 틀렸고 방향은 같다. 정답지는 면책 적용인데 모델은 정성 조건 미충족으로 면책을 보류했다. 세움건설은 "서면" 통지 여부가, 누리에너지는 "합리적으로 통제할 수 없는 사유"라는 사실이 사건 설명에 없다는 이유였다(`eval/results/real/report_port_congestion.json`의 `reasoning`). 둘 다 배상금을 잡는 쪽으로 틀렸고, 프롬프트가 요구한 보수적 방향이다.

추출 오차가 판단 오차로 이어진다. 정성 조건을 하나 더 적으면 그 조건의 충족 여부를 물어야 하고, 사실이 없으면 미충족이 된다. 세움건설이 그런 경우다. 그래서 기본 출처(실제 모델 추출)의 웹 조치 보드에서는 세움건설이 "통지만으로는 면책 안 됨"으로 나온다. 태풍 시나리오에서 "12h 통지를 지켰다면 0원"이라는 설명은 정답지 출처 기준이다([README 6절](../README.md#6-측정-결과)).

**실제 모델 조건으로 돌린 정책 비교(2회차 보고서).** 출처: `eval/results/real/report_*.json`, `run.log`, 정답지 값은 `facts.scenarios_mock`.

| 시나리오 | 계약 조건·판단 출처 | 마감 임박 순(기존) | 배상 노출 순(ClauseTower) | 절감 |
| --- | --- | ---: | ---: | ---: |
| 태풍 상륙 | 정답지(mock) | 12,834,000 | 2,996,500 | 76.7% |
| 태풍 상륙 | 실제 모델 2회차 | 12,834,000 | 2,996,500 | 76.7% |
| 항만 적체 | 정답지(mock) | 4,770,000 | 1,842,500 | 61.4% |
| 항만 적체 | 실제 모델 2회차 | 8,925,000 | 3,213,500 | 64.0% |

태풍은 두 출처의 총 배상금이 같다. 항만 적체는 모델이 세움건설·누리에너지의 면책을 보류해 두 고객의 배상금이 계산에 들어가므로 총액이 커졌다. 보수적 오차가 금액을 키우는 방향으로 드러난 것이다.

**1회차와 2회차의 차이**(추출 1항목, 판단 1건)는 프롬프트 수정 효과와 실행마다의 편차가 섞여 있다. 같은 프롬프트로 반복 실행하지 않았으므로 둘을 나눌 수 없다.

### 4-4. 측정 기록의 출처 표기

- 2회차 보고서는 실행 직후 그대로이고 기존·ClauseTower 총액(`policies.deadline_first`·`exposure_first`)이 `run.log` 시나리오 줄의 `base=`·`ours=`와 같다(태풍 12,834,000/2,996,500, 항만 적체 8,925,000/3,213,500). 2회차 `run.log`에는 정책 이름이 없다.
- 1회차 보고서는 정책 정의를 바꾼 뒤 `demo --from-reports … --resim`으로 시뮬레이션만 다시 돌렸다. LLM 결과는 그대로라 채점 값과 무관하다. 그래서 `real_prev/run.log`의 정책 이름·총액은 보고서와 다르다.
- 2회차 채점 파일의 `report` 필드는 채점 당시 경로(`out/real_v2/report_*.json`)이며 저장소에 없다. 그 보고서가 `eval/results/real/report_*.json`이다. 2026-11-02에 다시 채점한 값은 추가된 키 두 개를 빼면 추적 파일과 같았다.

상세는 [`eval/results/real/README.md`](../eval/results/real/README.md)에 있다.

## 5. 정책 비교와 다중 시드

### 5-1. 방법

- 정책은 "트럭이 빌 때 대기 화물 중 무엇을 먼저 보내는가"만 다르고 나머지는 같다(`src/clausetower/sim.py`). 정책 정의는 [README 5-4절](../README.md#5-4-배차-정책과-시뮬레이터), 수식은 [아키텍처](architecture.md)에 있다.
- 계약 조건과 면책 판단은 정답지를 쓴다(mock).
- 네트워크는 허브 1곳, 노선 8개, 트럭 8대, 화물 56건(건당 1적재)이다.

## 7. 재현 명령

먼저 [설치·실행 가이드](setup-guide.md)대로 `pip install -e ".[dev]"`로 설치한다. Windows·사내망의 주의 사항도 그 문서에 있다. 아래 명령은 추적 중인 측정 파일(`eval/results/`)을 덮어쓰지 않는다. 출력은 `out/` 아래로만 간다.

```bash
pytest -q                                                       # 71 passed
python -m clausetower demo --llm mock                           # 5-2절 숫자. out/demo/report_*.json(엔진 대조 입력)

# 다중 시드(5-3절). --out을 꼭 준다. eval/run_eval.py의 기본 --out은 추적 폴더 eval/results다
python eval/run_eval.py robustness --seeds 30 --out out/eval    # 또는 python -m clausetower eval --seeds 30 (기본 out/eval)
git diff --no-index out/eval/robustness.md eval/results/robustness.md   # 출력이 없으면 같다

# 실제 모델 채점(4-2절). LLM을 부르지 않고 저장된 보고서만 채점한다. --save가 없으면 화면 출력만
python eval/run_eval.py extraction eval/results/real/report_typhoon.json
python eval/run_eval.py extraction eval/results/real/report_port_congestion.json --save out/eval/extraction_port_congestion.json
python eval/run_eval.py extraction eval/results/real_prev/report_port_congestion.json   # 1회차
python eval/run_eval.py extraction out/demo/report_typhoon.json                         # mock: 100%, 엄격 인용 0.75

# 웹 엔진 대조(6절). mock 데모를 먼저 돌려야 한다
python scripts/build_site.py && node scripts/verify_engine.js   # 36/36 checks passed
pytest -q tests/test_web.py -k panel                            # 조작 패널 입력 75케이스
```

`--save`는 폴더를 만들지 않는다. 위 순서대로 robustness를 먼저 돌리면 `out/eval/`이 생긴다.

**실제 모델 재측정(과금, 실행하지 않음).** 2회차 기준 호출 24회, $2.06, 실제 소요 약 101초였다(측정). 결과는 `out/real/<시나리오>/report.json`에 저장되며 추적 폴더를 건드리지 않는다.

```bash
CLAUSETOWER_LLM=claude-code python scripts/real_run.py typhoon port_congestion
python eval/run_eval.py extraction out/real/typhoon/report.json --save out/eval/extraction_typhoon_new.json
python eval/run_eval.py extraction out/real/port_congestion/report.json --save out/eval/extraction_port_congestion_new.json
```

```powershell
$env:CLAUSETOWER_LLM = "claude-code"
python scripts/real_run.py typhoon port_congestion
python eval/run_eval.py extraction out/real/typhoon/report.json --save out/eval/extraction_typhoon_new.json
python eval/run_eval.py extraction out/real/port_congestion/report.json --save out/eval/extraction_port_congestion_new.json
```

`scripts/real_run.py`는 호출 횟수·대체 횟수·누적 비용과 마지막 줄의 사용량 JSON을 표준 출력에 찍는다. 이것을 저장해 두면 `run.log`와 같은 근거가 된다. 채점 출력의 `llm_fallbacks`가 0인지 먼저 본다. 0이 아니면 정답지 대체가 섞여 정확도가 실제보다 높다. 다른 LLM 모드(`anthropic`, `openai`)와 환경 변수는 [설치·실행 가이드](setup-guide.md)에 있다. `demo --from-reports <폴더> --resim`은 보고서를 제자리에서 덮어쓰므로 `eval/results/` 아래에 직접 돌리지 않는다. `out/`에 복사해서 돌린다.
